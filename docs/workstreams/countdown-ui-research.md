## Primary evidence and limits

The author's [HamClock 4.22 User Guide](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf) identifies version 4.22 / January 17, 2026. Relevant anchors are [printed 4 / PDF page 6](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=6) main screen timer entry, [printed 11 / PDF page 13](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=13) paragraphs Stopwatch, Count down and Big Clock, and [printed 16 / PDF page 18](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=18) external IO table. Two front-matter pages precede printed page 1. No original code, screenshot or hardware was copied.

**High confidence, documented summary:** Countdown duration is adjustable by clicking above/below the configured value, with a one-minute minimum. While active, remaining time replaces the main stopwatch icon; it can also occupy a selected pane or appear in Big Clock. Clicking any of those locations restarts the countdown; holding the main icon for three seconds opens Stopwatch. Big Clock has a menu supporting clock formats, zones, date/weather/seconds and basic countdown/alarm controls. The separate alarm paragraph specifies click-to-cancel and 60-second alert timeout; it does not establish countdown alert timeout. The external IO table describes countdown restart input and green/red LED states; this is hardware behavior, not evidence of native expiry visuals or sound.

**Unknown from the inspected guide:** duration maximum/step sizes, exact countdown time format and fractional rounding, expiry screen/flash/audio behavior, countdown acknowledgment semantics, pause/resume controls, duration editing while active, restart/reboot/suspend restoration and timer persistence. Do not infer screen colors from LED colors or reuse alarm timeout as countdown policy. Documentary evidence does not establish executable feature parity. Confidence is high for the quoted page mapping/summary, low for any unstated behavior; these unknowns require further primary evidence or an explicit replacement policy.

## Existing code boundary

The native stopwatch dialog borrows caller-owned `StopwatchState` and presentation references; both must outlive it. Actions/ticks copy candidate state, sample an injected clock once, prepare text, then commit; failures preserve shared state and report a visible error. Its 50 ms `QTimer` is a view refresh mechanism; hide stops view ticks, show catches up. It uses native labels/buttons, plain text, explicit status, >=44 logical pixel controls, tab order, existing System/Light/Dark styling and a compact 480x300 default. It is a useful pattern, not a countdown service: copying its model into another dialog would create independent timers.

The current CT0 contract has immutable one-minute..seven-day duration, Idle/Running/Paused/Expired, checked monotonic instants, atomic rejection, Start-as-restart, Stop-as-pause, Resume and Reset. Seven days and pause/resume are replacement policies, not original limits/features. Expiry clamps at zero and latches an instance-scoped pending event; `acknowledge(run_id, now)` clears it without resetting the expired phase. Run IDs may repeat across separate instances; they are explicitly not persistence identities. Reconfiguring duration requires a new service instance. Before any UI code, independently freeze these semantics and the relationship between model expiry and displayed notification.

## Original shared-service and presentation proposal

Use one application-owned countdown service per timer, owning model, injected monotonic clock, instance identity and subscriber lifetime. All operations occur on the QApplication thread; command processing and publication serialize there. Views hold a guarded handle (or a documented owner lifetime), not an unchecked reference to an object that a duration editor can replace. Root owns the application service integration and shared build wiring. If the service is replaced, invalidate old handles/subscriptions before destroying it; snapshot/run IDs alone do not guard dangling references.

Acknowledge commands carry **service instance identity plus run_id** captured from the event being displayed. Issue an acknowledgment token only for an actually pending expiry; controls cannot fabricate one from a running snapshot. Reject a stale instance before calling the model. Do not reread the latest run ID on click: an old expiry banner must never acknowledge a new run after restart/reconfigure. Use an original opaque lifetime token; persistence identity, if later introduced, is a separate reviewed schema. Guard delayed callbacks similarly and test replacing the service while a banner is visible. Never assume `run_id == 1` means the same event in two objects.

One refresh/action samples the clock once and advances the model before producing an immutable presentation snapshot. Publish the same snapshot to dialog/pane/Big Clock; do not let each view subtract its own tick interval or maintain a deadline copy. Coalesce redundant view updates. Define a reentrant subscriber-command policy (defer or reject) so a synchronous callback cannot mutate the service halfway through publication; subscriber errors must not roll back an already committed expiry or skip other views silently. View closure does not reset/pause/cancel a running timer. Reopening catches up from the clock, with visible failure if the clock reverses or fails. Define the actual monotonic adapter's suspend behavior separately; QTimer delivery punctuality is not elapsed-time accuracy.

Proposed display policy: show configured duration and named state; while Running, round a positive remaining duration **up** to the next displayed second, so a timer never appears expired before the model deadline. At expiry show zero and an explicit “Time elapsed” state. Formatting is bounded integer arithmetic (quotient/remainder instead of overflow-prone adding a second); days/hours are supported through the product cap. Paused and Idle are distinguished, and invalid commands preserve prior value with a readable error. This rounding/wording is a product choice needing review, not manual behavior. Countdown count direction differs from the stopwatch's elapsed truncation policy.

Expiry notification is latched until explicit acknowledgment/restart/reset for the first integration proposal; do not invent a 60-second automatic timeout. Acknowledge dismisses notification across views, leaving Expired/zero. A restart gesture starts the configured full duration and creates a new run identity. Keep explicit “Restart” and “Dismiss alert” controls separate so acknowledgment cannot accidentally restart. If the documented main/pane value click is implemented, preserve restart semantics and provide a visible equivalent button for keyboard/accessibility users. The first version has no audio, GPIO, radio commands or implicit system changes.

First integration is **session-only**: closing a view preserves a running service, exiting the application discards it, and the UI discloses that timers are not restored after restart. Configuration-only persistence and active-run restoration need separate approval/contracts. A saved monotonic deadline cannot be reused after reboot. If continuity is later chosen, record clock basis, duration/configuration revision and event identity, validate an atomic versioned settings record, and define missed/expired-at-start behavior explicitly. This is distinct from alarm civil-time/DST scheduling.

## Two paths, two steps ahead

| Path | First bounded step | Second step | Risk / recommendation |
|---|---|---|---|
| A: shared monotonic service, compact dialog plus dashboard pane | Freeze service/formatter/event token boundary; implement independent tested dialog borrowing a guarded service. Keep current stopwatch separate. | Root mirrors its immutable snapshot in the existing dashboard and later Big Clock; same command boundary across all views. | Smallest auditable progression, reuses accepted native styling. Owner lifetime/token correctness must precede duration replacement. Preferred proposal. |
| B: dedicated full-window timer view with mirrored pane | Use the **same** shared service but build a larger timer window with explicit exit/back and configuration controls. | Add compact dashboard mirror and Big Clock integration, validating simultaneous subscribers and resizing. | Better distant readability may suit kiosk use, but larger scope/layout work and state duplication temptations. Full-window view does not imply Big Clock parity. |

Both paths must preserve the accepted softer warm/slate UI: clear type hierarchy, restrained surfaces, system font, existing theme helper and visible focus; no gratuitous glow/game styling. Touch has visible >=44 logical pixel controls and duration edit affordances with named units. Keyboard and accessibility users get standard controls, explicit status and equivalent restart/navigation actions. A three-second hold is an additional compatibility gesture, not the only navigation. Cancel on release-before-threshold, pointer departure, hide, focus loss or service invalidation; completing the hold must suppress the subsequent short-click restart. Test keyboard alternative and no unintended activation. Do not announce every tick through a screen reader; announce meaningful state changes and keep remaining time queryable.

Qt minimum remains 6.4. Use existing Widgets/QTimer/context-bound callbacks; do not rely on Qt 6.8 QChronoTimer or newer theme APIs. [QTimer documentation](https://doc.qt.io/qt-6/qtimer.html) describes event-loop/thread affinity and possible late delivery: presentation timers are not real-time alarms. [QChronoTimer](https://doc.qt.io/qt-6/qchronotimer.html) is explicitly since 6.8. Ordinary button/label metadata is not accessibility certification; independent actual computer-control testing plus Pi touchscreen and Linux accessibility evidence remain mandatory.
