## Shared replacement contract and failure behavior

Proposed pure model, independent of Qt/network: `InstrumentId`, explicit `Unit`, `Sample { observed_at_utc, value, quality }`, `ForecastSample { issued_at_utc, valid_at_utc, value }`, `SeriesSnapshot { provider_id, instrument_id, samples, forecasts, status, fetched_at_utc, source_revision, attribution }`. Status is one of `Unavailable`, `Loading`, `Current`, `Stale`, `OfflineCached`, `Error`, `Disabled`, `Unsupported`. Images additionally retain channel, observation timestamp, dimensions and attribution. Keep observed time, fetch time, forecast issuance and forecast validity separate. A successful HTTP response containing an old observation does not restore `Current`.

State rules for **every** catalog entry:

- Initial network-enabled request: Loading with descriptive text; no fabricated zero/chart/image. No provider configured or permission unresolved: Unavailable with a reason and source information action.
- Valid finite observations: display value, unit, source and observation age. Missing/null/sentinel points create graph gaps; never substitute zero, connect a line across an outage, or silently carry an older value forward as current.
- Timeout/error after usable cache: preserve the last good value, visibly mark stale/offline and its timestamp; no usable cache: Error or Offline without readings. Atomic cache replacement follows successful schema/quality validation only.
- Forecasts remain forecast-labelled and visually distinct from measurements. Simulated clock offsets must not change freshness/HTTP scheduling, although a propagation request may explicitly use a chosen modeled instant.
- Rotation pauses while menus, editor, focused chart inspection or confirmation is active; a pending request completing for an old pane cannot replace a new selection. Request generation/selection token required.
- Proposed staleness thresholds are per-product configuration with documented defaults after cadence measurement; no universal five-minute threshold. Use monotonic time for deadlines/backoff and UTC for displayed data ages. Suspicious future timestamps get an error/quality marker, not indefinite freshness.

For utility Auto, retain a policy interface `rank_space_weather(snapshot) -> ordered ids` with deterministic ties and missing-data behavior. **Original ranking weights remain unknown**; do not ship an arbitrary ranking as parity. Ordinary manual selection/rotation can proceed without Auto.

### Additional catalog families: explicit handoffs, not omission

DX Cluster, Live Spots, On The Air, DXPeditions, Contests, ADIF, Rotator and Countdown are selectable instrument choices and must have catalog IDs immediately, even when their independent modules are not ready. Each is Unavailable with the relevant dependency reason until integrated. Assign detailed radio/logging/spot contracts to their own streams; do not fetch or copy their content under a generic space-weather permission.

Proposed required interfaces: spot families provide bounded `SpotListSnapshot` and typed `ProposeDx/OpenSourcePage/RequestRadio/RequestRotator` commands; ADIF provides a bounded local-file snapshot; events provide timezone-aware immutable `EventListSnapshot`; Rotator provides feedback/status and explicitly gated movement commands. The pane container itself must not execute hardware commands or interpret a provider URL as code. Menu/title selection must not accidentally transmit or move a rotor. Current provider permissions for POTA/SOTA/WWFF, PSKReporter/WSPR/RBN, NG3K/DXNews/WA7BNM and ADIF country assets remain dedicated research gates, not approved here.

**Countdown is an explicit clock-module handoff**, not a network instrument, a stopwatch substitute, a SpaceWx Auto item, or the display on/off timer. [Manual printed p.11](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf) explicitly documents a Countdown pane when countdown is active and a restart action; it describes the stopwatch, alarms and Big Clock separately. Proposed interface: `CountdownSnapshot { remaining_duration, run_state, configured_duration, generation }` plus typed `RestartCountdown/OpenTimerControls` commands supplied by a separate clock owner. I01 must include its distinct catalog ID and availability dependency; exact inactive-pane selection and restart/persistence semantics still need pinned-source/runtime confirmation. I11 clock handoff tests should inject monotonic time, verify decrement/expiry/restart across pane rotation without resetting merely because a pane becomes hidden, and distinguish elapsed stopwatch time, UTC simulation and scheduled display dimming. Native tests must verify textual remaining duration, accessible running/expired state, reachable restart, no unsolicited alarm/hardware action, and return to the same configured pane after opening timer controls. Any broader alarm/stopwatch behavior belongs to that independently researched clock stream; do not label those separate screens as selectable panes without evidence.

Moon is a separate astronomy family: accept `LunarSnapshot` with phase/DE-relative angles/rise-set/radial-velocity and EME-tool command. Exact lunar texture permission and ephemeris/model accuracy need the astronomy stream; do not reuse original embedded moon images.

NCDXF utility needs a deterministic UTC schedule and current beacon metadata, not live reception claims. [NCDXF introduction](https://www.ncdxf.org/beacon/intro.html) identifies five frequencies14.100/18.110/21.150/24.930/28.200MHz and18beacons. Schedule/locations and asset-use terms require separately pinned primary evidence. Brightness/on-off utility depends on actual platform support, calibration and timezone/schedule; Unsupported is appropriate on incapable hardware. Neither should request elevated privilege from a pane click.

## Security and provenance review before live integration

Proposed policy: data fetching is an explicit application setting; no telemetry and no unsolicited station-location transmission. Space-weather global feeds need no DE/DX coordinates. Propagation/weather requests may disclose coordinates, parameters and public IP; surface that fact when enabling the source. Request transport is a single shared, reviewed owner, not one network client per widget.

Required transport contract: HTTPS certificate verification; fixed approved provider identities and bounded paths; no user-supplied arbitrary URLs, credentials-in-URL, silent downgrade, or redirects to another host. If provider redirects change, update an allowlist with evidence instead of following unrestricted redirects. TLS/connect/read/deadline bounds, response byte limit, decoded-image pixel limit, item-count/depth/string bounds, cancellation and a single in-flight request per product. Cap compressed and decompressed content. Finite numbers only, strict timestamps/units/quality, duplicate/conflicting keys rejected for required security-relevant fields. Strings render as plain text; provider HTML/scripts never render inside native widgets.

Proposed initial bounds for fixture implementation (not claimed provider maxima): numeric payload2MiB,10000samples/series, at most16series, text128KiB, image2MiB/1024²pixels; reject with a recoverable message if a documented legitimate product exceeds a bound, then review that limit. Do not quietly truncate observations in a way that changes extrema/trends. Cache retention and historical downsampling require separate explicit policy. No shell command interpolation; a local model runs by fixed executable/argument contract and private bounded input/output files, no inherited network credentials.

Respect [NWS usage guidance](https://www.weather.gov/disclaimer): fetch according to production cadence, request only required data, and space retries at least one minute. Proposed backoff60s/120s/300s/900s with jitter and maximum15min, respecting longer Retry-After, is a replacement default subject to product/provider requirements. No polling per UI frame, per displayed slot or per clock tick. Shared feed snapshots let three panes/utility consume one request. Verify idle networking and retries on a real Pi3 before support claims.

Each provider gets a provenance record containing owner, exact endpoint, schema/revision, date checked, policy link, attribution text, redistribution/cache/export position and review result. Retain upstream attribution independently of MIT code. External media/data must not be relicensed as application source. Permissions unresolved means no production fetch/distribution, while pure models and synthetic fixtures remain implementable. This research has sent no permission-request emails or other messages to providers.

## Two paths and two steps ahead for uncertainty

### Propagation: retain original model vs explicit alternative

**Path A: local VOACAP with an original adapter.** High confidence that NTIA publishes a conditional redistribution policy; unknown exact selected Linux engine/port/coefficients chain and Pi3 cost. Step1: pin engine distribution plus all coefficient/antenna files, preserve NTIA notice, inspect every component license, compile outside app with no runtime download. Step2: obtain independent numerical oracle fixtures using original assumptions and measure24hours×bands latency/RSS/cancellation on Pi3. Only then assign I09. This avoids reliance on the prohibited online service, but does not automatically certify full numerical parity.

**Path B: approved remote VOACAP backend or explicitly labelled alternative model.** Step1: independently inspect a backend's published API, model revision, coefficient provenance, access/privacy/rate-limit and redistribution terms; obtain actual written service permission if needed through a separately authorized outreach. No such permission exists in this packet. If using REC533/another model, inspect its primary specification/code/data rights and obtain a **user product decision** because model results differ. Step2: same fixed input suite against PathA/reference; compare tolerance/error/coverage and offline behavior before offering it. A generic SFI/Kp-to-good/fair/bad heuristic cannot replace original band/hour reliability. Recommendation: pursue PathA first while building I08 independent request model; keep B as a documented fallback.

### SSN rights and source fidelity

**Path A: original SILSO index.** Step1: independent review of current CC BY-NC terms and intended donations/distribution/cache/export; resolve whether written permission is needed, without contacting anyone until authorized. Step2: capture daily and monthly source fixtures with attribution/provisional flags, then integrate behind I05.

**Path B: NOAA-produced SWPC-observed series.** Step1: verify exact ownership/reuse terms and numerical definition (not SIDC rehost) in product metadata. Step2: compare both series over a known interval, quantify effect on propagation and ask for an explicit source-fidelity decision before changing default. Keep distinct IDs/labels; “NOAA” transport does not imply the same SSN.

### SDO and original backend compatibility

**Path A: directly licensed NASA/SDO browse products.** Step1: pin image types/resolutions, timestamps and exact credit/exception policy. Step2: compare original channel menu/image orientation and DE overlays, then build bounded decoder/provider adapter. **Path B: compatible backend images.** Step1: inspect backend standards + transformation attribution + underlying image permissions and server access policy; a backend MIT license is not media clearance. Step2: fixture-compare timestamps/channels/decode and consent/privacy/rate behavior. Direct512px images are the provisional Pi-conscious recommendation; original channel parity still needs comparison.
