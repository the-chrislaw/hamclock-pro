## Primary facts and version evidence

The [US Naval Observatory Gregorian rule](https://aa.usno.navy.mil/faq/leap_years) excludes ordinary century years from the four-year leap cycle unless divisible by 400. Thus 1900 and 2100 are common, 2000 and 2400 leap. **High confidence.** Applying this calendar before historical adoption is a proleptic product convention, not a reconstruction of local historical legal calendars.

[Qt QDate](https://doc.qt.io/qt-6/qdate.html) documents Gregorian validation, invalid year zero and a substantially wider internal date range than four-digit years. [Qt QTime](https://doc.qt.io/qt-6/qtime.html) permits hours 0..23, minutes/seconds 0..59 and distinguishes formatting with AM/PM from 24-hour output. An invalid formatted time may produce empty text: emptiness must not become a fabricated valid midnight. **High confidence for these documented facts; narrower product bounds below are proposals.**

Current documentation was retrieved as Qt 6.12, so it is not blanket proof for our 6.4 baseline. Version-specific `doc.qt.io/qt-6.4` pages and browser views of tagged files failed. After a research-only network grant, bounded official Qt repository files were retrieved into `/private/tmp/hamclock-resumed-model-audit/`, not the repository. **High confidence in declarations/QDoc at tag v6.4.3, not a baseline executable build.**

Neither civil-time formatting nor UTC-instant-to-zone display authorizes resolving user-entered ambiguous times or scheduling DST alarms.

## Proposed pure digital contract: CB1a

These are **original replacement policies for API review**, not HamClock defaults, exact menu behavior, date style or certified feature parity.

- Accept an explicit optional civil value containing Gregorian year 1..9999, month/day, hour 0..23, minute/second 0..59. Validate the whole date even if date is hidden, and second even if seconds are hidden. Reject year zero/BCE, impossible days, 24:00, 60th seconds and unknown enum values; do not normalize them into another instant. Source-validity absence is separate from malformed supplied fields.
- Format bounded ASCII `YYYY-MM-DD` when date requested, `HH:MM[:SS]` for 24-hour, and `HH:MM[:SS] AM/PM` for 12-hour. Midnight is 12 AM, noon 12 PM; 13 becomes 01 PM. Date is ten bytes and longest time eleven bytes. No external locale strings, format-language parsing, weekday calculation or borrowed buffers in this slice. AM/PM remains explicit when seconds/date are hidden.
- Preserve explicit UTC/DE selection and actual/preview basis. Absent civil fields produce a named unavailable state and no numeric time/date; do not convert `SyncStatus::Unknown` into missing time. `ClockState` already supplies actual UTC even at epoch zero when synchronization evidence is Unknown. Validate synchronization/basis/zone enums independently, including when source fields are absent.
- A caller-supplied DE civil value is evidence supplied by that caller, not proof of the zone mapping or UTC relationship. The formatter neither adds offsets nor reads the host zone. Source/capability absence never rewrites DE to UTC. Unsupported Analog preference must remain visibly unsupported by a digital-only slice rather than silently changing the preference.
- `show_date=false` suppresses only date output. `show_seconds=false` suppresses only second output; never round a hidden fraction forward. Actual/preview indicators and unknown/unsynchronized evidence remain independently queryable. Unknown synchronization means accuracy unestablished, not synchronized, healthy or missing. No freshness/alarm/countdown computation uses preview.
- Validate complete immutable input before returning owned output; caller prepares that output before committing its own state. No formatter state/history, clock reads, service activation, provider data, alarm tokens or fake current observations.

Product decisions still open: localized date/hour text, weekday composition, BCE support, preview opt-in/default, DE zone selection/offset policy, display of unsynchronized warning and the final unavailable wording. The bounded ASCII/four-digit proposal allows coding without deciding those broader features. The CB1a writer must reconcile its concrete header with these assumptions through its own independent gate; this document is not permission to change another owner's files.

## Adapter coding ticket and fixtures

**CB2a, proposed exclusive new files** `src/qt/big_clock_civil_adapter.hpp/.cpp`, `tests/qt_big_clock_civil_adapter_regression.cpp`; root must assign ownership before implementation. Accept injected `UtcSeconds` plus explicit source validity and requested zone evidence. For UTC display, use the reviewed POSIX/Gregorian product range `-62135596800..253402300799` (year 1 start through year 9999 final second), call the explicit UTC overload, then validate all returned fields. These constants were independently calculated with Python `calendar.timegm` over literal tuples, not copied implementation. Invalid/extreme input returns a typed unavailable/error result before any Qt conversion; pre-reject INT64_MIN/MAX. Proposed fixtures: epoch 0 -> 1970-01-01 00:00:00; -1 -> 1969-12-31 23:59:59; 951782400 -> 2000-02-29 00:00:00; 4107542400 -> 2100-03-01 00:00:00. Separately peer-verify constants/oracles before code promotion.

**CB2b, next exclusive files chosen after gate:** convert an already valid UTC instant with `toTimeZone()` into explicit reviewed DE zone; validate zone, conversion and final product year bounds again, including offset-driven date crossings at both ends. Carry station revision and zone/offset evidence so stale location results cannot populate a new station. Never pass `Qt::TimeZone` to the TimeSpec overload as a substitute for a zone object; tagged QDoc explains its local-time fallback. Never call host `toLocalTime()` or `systemTimeZone()` as inferred DE. Instant-to-zone conversion is distinct from constructing an ambiguous local civil input.

**CB1a adversarial tests:** Gregorian century/leap-day cases, every invalid month/day/hour/minute/second/enum; year 1/9999 boundaries; midnight/noon/23:59:59 with both hour styles and date/seconds switches; missing fields with known/Unknown synchronization; zero epoch available through adapter; preview and DE labels preserved without date/time fallback; invalid supplied fields rejected even if hidden; owned-view lifetime and allocation rejection preserving caller state. Date rollover comes from caller/adapter fields; pure formatting must not claim to compute it.

## Provenance, confidence and remaining gates

[IANA's primary timezone reference](https://data.iana.org/time-zones/tz-link.html) describes public-domain tz data, political changes and a database that is not authoritative legal time. This does not clear a station-boundary dataset, Qt distribution, host backend or third-party timezone mapper. Record the actual runtime backend/data revision and review distribution dependencies separately; no asset/database/runtime package is copied by this work.

High confidence: primary Gregorian rule; exact tagged Qt 6.4.3 declarations/QDoc; separation of existing source time and synchronization; bounded proposed formatter arithmetic. Moderate: future adapter architecture is implementable with the verified signatures. Unverified: actual Qt 6.4 target build, Pi behavior, host tz completeness, station timezone mapping, extreme adapter result behavior within requested zones, localization choices and original Big Clock preview/date semantics. No source copying, legal clearance, hardware support, accuracy, accessibility compliance or full parity follows from this research.
