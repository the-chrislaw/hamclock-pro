## Recommendation: skip the standalone equality guard now

Read proposed `src/app/de_clock_civil_snapshot.hpp` SHA256 `99b28415856ddc2094296d1b4ef8e3ed893ad56dc7f855b422c3246a16b8b90e`, current dashboard header `e0b34e36cb289e4b0ffe99015ceca72ea9f4e902fa79c80b2f0ff2eceab04667`, implementation `935c17b86947ca72c60ff5e3a7d02b8c884c045110fbfe00c8ddd170f4d2d268`, frozen Big Clock input/dialog contracts, station persistence/editor and actual dashboard regression. **High confidence: do not implement the separate proposed guard for the present synchronous caller.** It compares two caller-supplied contexts and explicitly cannot verify owning session, civil payload or provenance. There is no current asynchronous completion, delayed lookup or converter cache to reconcile. Adding a second completed-context copy/equality API now duplicates settings/source validation without solving the missing integration. Correct equality is useful only when a real completion boundary exists; even then equal counters/values are not session authority.

Current dashboard has one GUI-thread timer which alone reads OS UTC, converts it and publishes an owned `BigClockDigitalInput`. Big Clock reads only that owned value through its injected callback. Conversion performs no callbacks or event-loop work, so station/configuration actions cannot interleave midway through a single conversion call. A modal dialog has a nested event loop between callbacks, which means source/configuration snapshots must be recaptured each operation; this does not create an asynchronous completion inside the guarded adapter. Existing dialog reentrancy guard remains required around its injected callback. This recommendation assumes no new processEvents, asynchronous lookup, external reentrant callbacks or shared worker writes are introduced.

The useful safety work is a direct synchronous bridge: retain the cached raw actual UTC optional from the sole timer; capture the validated dashboard-owned DE configuration snapshot; run the frozen UTC and manual adapters against that exact raw source; assemble one owned display snapshot with UTC/DE values and raw DE status/source/offset provenance; publish only after all preparation succeeds. Automatic supplies missing DE with an explicit unresolved reason; a manual Ready result alone supplies DE civil. Unknown synchronization stays independent, and no preview or shifted-calendar value replaces actual UTC. Product bounds remain those already reviewed. Source/configuration revisions are metadata, not authenticity/currentness proof.

## Smallest testable native integration prerequisites

1. Root owns one stable DE configuration instance for the dashboard session, initialized explicitly Automatic at the actual validated DE coordinates and with an explicit caller policy. Keep the existing sole OS UTC reader and cached source. An offset/mode action recomputes from the cached actual UTC immediately, including while Big Clock is open, rather than reading the clock independently or waiting a second with old civil values. Prepare conversion/output/text first, then the existing checked configuration transition and no-throw owned display publication; keep Qt postcommit rendering outside any catch that promises rollback. A failure must preserve old configuration/display or explicitly mark an unavailable state, never falsely show an old offset as current.
2. Root provides a small native manual configuration view or a clearly named entry within existing Big Clock Options, reusing the application-owned state. No new masthead entry is needed on the already constrained 800x480 dashboard. Draft edits do not configure time; explicit Apply performs one serialized action. Current Automatic/Manual, fixed offset/no automatic DST, session-only scope and failure status must be visible and accessible. Keep current native themes, 44 logical targets, keyboard focus, persistent error recovery and tested draft-fixup behavior. A read-only getter/owned test snapshot can expose raw source/configuration/provenance for deterministic integration assertions without a mutable state seed or global token API.

The current `BigClockDigitalInput` intentionally contains civil values and synchronization only; it cannot carry the manual offset or unavailable reason. Do not extend the pure formatter into a configuration service. The native caller needs one coherent owned snapshot or equivalent co-committed provenance fields; if the native dialog contract changes, use a header-first gate so displayed DE provenance updates with the same source/configuration as the civil value. Updating an opening-only description is insufficient when configuration changes during the modal's nested event loop. A separate equality helper does not solve this provenance gap.

Validated DE coordinate changes must invoke the existing canonical set_location reset before any new DE civil publication. Same canonical dateline/signed-zero coordinates preserve manual state under its explicit reviewed policy. Callsign/DX/appearance-only saves must not reset DE. Invalid/cancelled/failed station saves must preserve the existing session. The editor currently returns only after disk save, so unexpected reset/revision failure after that save cannot be described as a rolled-back station save; invalidate old DE civil and report the failure truthfully instead of attaching old-location manual data to the new station. Full-range helper exhaustion remains structural unless a real testable boundary is introduced without a public counter backdoor.

Required tests for the direct bridge/native view: injected zero/missing source and fixed calendar goldens; each Manual/Automatic transition; immediate refresh from identical cached source; second/date/quarter-hour offset crossings; changed versus canonical-equal station locations; failure/cancel preserving configuration and saved bytes; actual/raw source never replaced by shifted seconds; same snapshot used for UTC, DE and provenance; Unknown sync retained; close/reopen session settings; themes, enlarged fonts, AX values/checked states, keyboard paths, touch bounds and compact geometry. Independent strict regressions/fresh suite precede actual native computer-control tests; offscreen results cannot substitute for the latter.

## Explicit offset UI policy and two steps ahead

The [original guide, printed 13 / PDF page 15](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=15), previously independently reviewed, documents manual/automatic correction, location-change reset and restart persistence. It does not establish exact numeric bounds or step in the evidence available here. The existing pure configuration deliberately accepts caller-selected signed-second bounds; adopting a numeric UI cap is a replacement product choice, not an inferred original restriction.

**Moderate-confidence recommendation for root's explicit UI policy:** use a fixed offset range ±24 hours, retain integer-second precision, and a bounded signed `HH:MM[:SS]` draft with explicit Apply. Allow ±24:00 only at zero minutes/seconds; reject malformed, out-of-range and intermediate edits without clamping or applying restored cached text. A clearly stated range is more usable than exposing arbitrary signed64 seconds; preserving seconds avoids silent rounding of valid model values. Root may choose a different explicit reviewed policy before the native header freezes. This routine product choice need not block already authorized development or be presented as an original legal-zone bound. New UI text should explain fixed offset and no automatic DST using plain language.

First integration step: native session-only Manual/Automatic desire controls plus the synchronous display bridge; Automatic remains unavailable, original restart persistence remains a documented gap. Second step: separately owned versioned station schema/migration and atomic save of reviewed mode/offset, then separately reviewed automatic mapper/backend data acquisition, resources/licensing and stale-session protocol. An actual asynchronous mapper or delayed cache would justify a stable owning lifetime plus checked request/config/location revision binding, validation of returned payload/provenance and rejection after owner destruction or reconfiguration. The proposed equality helper alone is insufficient for that future protocol. No mapper/provider/persistence or timing/DST policy is approved by this review.

**Scoped decision:** skip the unneeded header implementation; proceed to root's direct synchronous bridge/native manual-control header proposal. This architecture review grants no production/source/UI/hardware/legal/parity claim and no automatic fallback. Confidence is high for the actual synchronous-code assessment and missing provenance field; moderate for UI sequencing/explicit range recommendation; unresolved for original numeric controls, persistence migration, mapper choice and target-device execution.
