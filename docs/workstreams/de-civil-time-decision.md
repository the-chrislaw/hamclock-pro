# DE civil-time display: evidence and staged choices

October 11, 2026. Research only, awaiting independent review. Exclusive document; no application source, station UI/settings, shared builds, Git, runtime clock, radio, device, dependency or transport changes. This report proposes implementation boundaries; it does not authorize a timezone mapper or clear a data license. Prior UTC/civil research remains frozen.

## Final-original documentary behavior

The author's [HamClock 4.22 guide](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf), January 17, 2026, provides concrete DE timezone requirements:

- [Printed 5 / PDF page 7](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=7): DE combines station location with local date/time, and its offset control allows correction.
- [Printed 13 / PDF page 15](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=15): DE/DX timezone control offers manual offset or automatic location-based offset/DST. Selection persists across restarts; changing location resets automatic. DST updates may lag approximately an hour.
- [Printed 11 / PDF page 13](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=13): changing preview UTC is distinct from correcting DE timezone; Big Clock can select UTC/DE.

**High confidence in these documented requirements.** Unknown: exact manual offset bounds/step, timezone mapper or data source/license, border/ocean accuracy, transition refresh/caching algorithm, named-IANA editing, historical/future preview interpretation and a guarantee that Big Clock uses a specific time basis. Explicit IANA editing is our proposed option, not a documented original control. The guide describes approximate automatic behavior; it does not justify copying an implementation or intentionally adding an hour of lag to a new reviewed adapter.

## Current project boundary

`StationSettings` contains DE/DX coordinates, callsign and appearance, with version-1 persistence rejecting unknown keys. There is no zone mode, offset or zone ID. `StationView` formats coordinates/locators/geometry without timezone inference. Station editing validates a draft before an explicit save; a new timezone schema/editor requires separately assigned migration, atomic-save and UI work.

`location_from_maidenhead` supports 2/4/6 ASCII characters and returns the southwest corner under an explicit replacement policy, not a center or a timezone. A locator cell and its chosen representative point are not proof of the user's legal civil zone. The same grid can intersect a boundary; guessing from longitude or feeding the current southwest corner into a mapper without disclosure introduces a new location assumption. No geometry routine currently performs a polygon lookup. Saved station revisions must bind any future lookup/conversion result; late replies must not populate a newly moved station.

`ClockState` separates actual UTC, preview and synchronization. `Unknown` synchronization is not absent time; epoch zero is available when supplied. Existing UTC civil conversion is not a DE adapter. A valid zone conversion does not establish source accuracy, NTP synchronization or alarm scheduling.

## Three modes and their consequences

| Mode | First display path | Benefits / limits | Two steps after initial adapter |
|---|---|---|---|
| Explicit user IANA ID | Reviewed caller-selected ID -> Qt named-zone conversion of an injected UTC instant -> validated DE civil fields with zone/offset evidence. | Avoids station-location disclosure and a boundary dataset. Backend availability/rules must be verified; users must select the appropriate zone. Named civil rules handle date-dependent offsets, while source accuracy stays separate. | First add bounded mode/ID configuration and reviewed station revision handling; then native selector/persistence migration with actual target/backend tests. Automatic location selection remains a separate full-parity requirement. |
| Explicit fixed UTC offset | Typed checked offset plus injected UTC -> checked arithmetic and reviewed civil conversion -> DE label including fixed-offset/no-auto-DST indication. | Smallest offline alternative and directly matches the documented manual concept. A fixed offset never tracks seasonal/rule changes by itself. Quarter/half-hour offsets and date crossings must work. | First pure offset adapter and configuration validator; then explicit offset editor/persistence and truthful indication. Add named/automatic rules later without pretending manual offset is automatic. |
| Automatic location/grid lookup | Explicit location evidence -> approved mapper -> named ID plus dataset/provider and station revision -> reviewed civil adapter. | Necessary documentary parity lane, but introduces boundary ambiguity, data terms, resources and potentially privacy/network dependence. A suggested zone needs override/correction. | First license/provenance and bounded mapper evaluation with border/ocean fixtures; then independent parser/index/API security and measured Pi resource tests; only afterward station UI and automatic mode integration. |

**Recommendation, moderate confidence:** progress with original pure explicit-IANA and explicit-fixed-offset contracts, maintaining no-inference/unavailable behavior until a caller actually configures one. Prepare automatic mapping independently as required parity work. The user's final feature requirement prevents dropping automatic mode; this sequence postpones its dependency without claiming it already works. No choice silently copies the host's local timezone into DE or adjusts actual UTC.

Potential product question, only when configuration integration actually blocks: “Offer named timezone and manual offset first, with automatic lookup still required before full-parity release?” This is not necessary to stop pure UTC/digital/adapter work. The already authorized overall scope remains unchanged, and no hidden timezone default is selected.

## Automatic lookup: offline versus remote

[Timezone Boundary Builder](https://github.com/evansiroky/timezone-boundary-builder#licenses) describes approximate OSM-based shapes with `tzid`, separate comprehensive/since-1970/current-time products, and separate **MIT code / ODbL output data**. Its documented border guesses and omissions matter; current-time merged shapes are unsuitable as proof for arbitrary historical previews. The current release size, compressed/uncompressed expansion, index design, parsing peak RAM and Pi latency were not measured. Do not invent a size budget or infer that a Python/JS mapper is acceptable in a native Pi 3 process.

[ODbL's primary license](https://opendatacommons.org/licenses/odbl/1-0/) includes notice, derivative-database share-alike and access requirements. The application code's MIT choice does not relicense a downloaded/simplified boundary database. Before using any pinned release, review actual DATA_LICENSE, attribution, transformation/distribution classification, release hash and provenance separately. This is a concrete unresolved data gate, not a claim that MIT application code must automatically become ODbL.

Offline path: pin approved data -> evaluate an original bounded index or separately approved dependency -> test polygon boundaries/holes/overlaps/antimeridian/oceans and ambiguous/no-zone results -> benchmark Pi RAM/startup/lookup. Enforce archive expansion/file/vertex/geometry caps before allocation, no path traversal or runtime downloads, and station revision checks. Do not silently choose the first overlapping polygon or nearest city as a legal-zone proof. Any grid-to-point policy must be explicit and revisable.

[Google's primary overview](https://developers.google.com/maps/documentation/timezone/overview) provides location-and-timestamp lookup over HTTPS. Its [billing documentation](https://developers.google.com/maps/documentation/timezone/usage-and-billing) requires billing and credentials. [Published product policies](https://developers.google.com/maps/documentation/timezone/policies) add attribution/privacy/terms and storage/display restrictions, including non-Google-map limitations. These need exact agreement/context review before use in our geographic dashboard; no request, account, API key, spending or permission was exercised here.

Remote path: approve provider terms and location disclosure -> design bounded HTTPS requests/credential storage/retry/caching under those terms -> original strict parser and stale-revision rejection -> offline/error UI and account/quota protection. Do not embed credentials in open-source code, send precise station locations implicitly, retry without bounds, or cache beyond reviewed terms. This is more operational work than an explicit user-selected zone; it is not the recommended first integration.

## Qt 6.4 and target-system gates

Exact [official tagged Qt 6.4.3 qtimezone.h](https://raw.githubusercontent.com/qt/qtbase/v6.4.3/src/corelib/time/qtimezone.h), previously retrieved/hash-verified in `big-clock-civil-time-contract-research.md`, requires feature `timezone` and declares IANA/fixed-offset constructors, validity, available-ID lookup and offset-at-instant APIs. Tagged [qdatetime.h](https://raw.githubusercontent.com/qt/qtbase/v6.4.3/src/corelib/time/qdatetime.h) exposes explicit named-zone conversion under the same feature. These are declaration evidence, not an executable baseline/backend test. Feature-disabled baseline builds need an explicit unavailable branch without including unavailable named-zone APIs. A pure fixed-offset adapter can use checked typed arithmetic and the UTC adapter without requiring a named-zone database.

[Current QTimeZone documentation](https://doc.qt.io/qt-6/qtimezone.html) warns that configured builds can still lack usable timezone data, such as missing Linux `tzdata`. It identifies platform/ICU backend differences and bundled CLDR data under its own terms. Verify actual build flags, backend/data provenance and zone availability on each target; do not equate an IANA ID's syntax with a valid installed zone. Current lightweight UTC representation introduced in 6.5 is distinct from baseline named-zone availability. Keep original API paths version-gated; no global warning suppression or Qt 6.7 transition-resolution reliance.

[IANA](https://data.iana.org/time-zones/tz-link.html) identifies public-domain tz data but warns of changing government rules and a non-authoritative database. That does not clear OSM polygons, CLDR, Qt distribution or a remote provider. Bound ASCII zone IDs, reject embedded NUL/control/path-like unreviewed forms, validate against the reviewed backend, and never execute an ID through a shell or read an arbitrary ID-derived filesystem path in application code.

[Official Raspberry Pi OS documentation](https://www.raspberrypi.com/documentation/computers/os.html) currently lists Trixie as latest and Bookworm as previous, with 32/64-bit editions. Debian publishes [Bookworm Qt Core 6.4.2](https://packages.debian.org/bookworm/libqt6core6) and [Trixie Qt Core 6.8.2](https://packages.debian.org/trixie/libqt6core6t64). These package listings support planning only: the user's actual image, architecture, installed Qt/tzdata/ICU, touch stack and time configuration have not been observed. Do not require an OS change or installation by inference. Qt's [datetime documentation](https://doc.qt.io/qt-6/qdatetime.html) explains platform time-range/offset limitations; a 32-bit OS alone does not prove which `time_t` ABI/backend is active. Run explicit before/after-2038 and historical/future tests on the actual target.
