2026-10-11 research only, awaiting independent primary-source peer review. This document is separate from CU1 publication and authorizes no clock/alarm/DST implementation, source edits, device access or dependency changes. User scope is full final-original HamClock 4.22 parity with the accepted softer native UI. Documentary evidence is a feature requirement inventory, not a claim that the current application meets it. ## Original behavior: confidence and anchors

Primary source is the author's [4.22 guide, January 17, 2026](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf). [Printed 4 / PDF page 6](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=6) shows the main timer entry. [Printed 11 / PDF page 13](https://qsl.net/g6nhu/hamclock/hamclockkey-4.22.pdf#page=13), paragraphs Stopwatch, Count down and Big Clock, specifies the following (**high confidence**, compact summary):

- Big Clock is a large dedicated clock. Clicking anywhere opens its options menu: analog/digital, UTC/DE, 12/24-hour, date information, DE/space weather, seconds, and basic alarm/countdown controls.
- Armed alarm time may appear in Big Clock. A firing alarm highlights that time; clicking cancels it, and alarm alerts expire after 60 seconds. Main-screen and stopwatch alerts are additional surfaces.
- Active countdown remaining time may appear in Big Clock and restart by clicking there. Main-icon and selectable-pane countdown surfaces also exist; a three-second hold of the main icon enters Stopwatch.
- The time paragraph distinguishes actual UTC from a shifted preview and unknown time. It does not specify Big Clock's preview-clock policy.

**Unknown from this guide inspection:** exact Big Clock menu labels/defaults, entry/exit gesture beyond the referenced timer entry, precise geometry/fonts/colors, analog 24-hour dial behavior, independent second-hand versus digital-seconds meaning, date composition, exact weather metrics/units/cadence, simultaneous DE/space-weather selection, alarm overlap layout, countdown expiry visuals/sound, active-view preference persistence and post-restart restoration. A main icon hold is not proof of a Big Clock hold gesture. Do not apply alarm's 60-second timeout to countdown. No original executable was exercised for these gaps.

## Current code and shared input boundaries

Read native dashboard, clock state, station view and instrument snapshot contracts. Current dashboard uses `QDateTime::currentDateTimeUtc()` in its local one-second refresh and labels it an operating-system UTC clock; it does not establish NTP accuracy or DE-zone conversion. Pure `ClockState` carries actual/display UTC, preview flag, monotonic elapsed and synchronization evidence, but does not format civil time, handle leap seconds, supply missing-source validity or implement alarms. Its Unknown synchronization is **not** missing UTC; never convert that enum into a blank time by assumption.

`StationView` supplies station/location/geometry text, not a timezone. `StationSettings` edits update the dashboard only after successful save. A location change must invalidate any outstanding location-specific weather/zone request through a revision guard. Do not infer DE time from host-local timezone or longitude. A separately reviewed source-validity and civil-conversion contract must provide DE date/time plus explicit zone/offset evidence.

The bounded instrument snapshot contract distinguishes unavailable/loading/current/stale/offline-cached/error and provenance, with actual UTC for age evaluation. It is not a whole DE-weather schema or complete space-weather panel. Reuse its status principles, then freeze family-specific types/units/ranges and permissions before real provider display. Missing/invalid measurements are never zero; forecast is separate from observed data. No synthetic readings may appear as Live/Current. A demo/replay, if explicitly supplied, stays visibly labeled with its time basis. A weather selection can remain selected while displaying “Unavailable”; never silently replace it with a different product.

Big Clock consumes one application-owned immutable clock/station/provider snapshot and the **same** countdown/alarm service identities as the dashboard/timer dialog. It has no competing system-clock read, independent countdown model, network acquisition or settings writer. Root owns shared source wiring. Closing/opening the view changes visibility only. Guard borrowed service lifetimes, delayed callbacks and command tokens against replacement; countdown acknowledgments require instance + run identity from an actually displayed pending event. Alarm identities require their own reviewed scheduler contract and cannot reuse countdown IDs.

## Original CB0 preference proposal

Define a pure bounded preference structure with typed `ClockFace {Analog, Digital}`, `ClockZone {Utc, De}`, `HourFormat {Twelve, TwentyFour}`, booleans for date/seconds/alarm/countdown, and `WeatherSelection {Off, De, Space}`. These exact enum names, Off option and mutual exclusion are replacement API proposals; the manual does not prove whether weather choices can be simultaneous. Validate every enum atomically. Store the user's desired selection independently of runtime availability; unavailable providers must not corrupt or silently rewrite preferences. No timezone ID, alarm schedule, weather payload or countdown deadline belongs in this preference object.

Proposed initial defaults: digital, UTC, 24-hour, date/seconds enabled, weather off, alarm/countdown information enabled when available. These are **not original defaults** and need product/API review. Appearance follows the existing app System/Light/Dark preference; avoid a competing theme setting. Preference persistence is a separate root/settings review and versioned schema, not implicit in CB0. First CB0 is in-memory only.

Proposed display time defaults to actual UTC or its reviewed DE conversion; if preview is later offered, expose a persistent “Preview” indicator and actual/preview basis to accessibility clients. Preview must not affect provider freshness, alarm scheduling or countdown elapsed time. If conversion is absent/invalid, display “DE time unavailable” with a correction route, not invented offset or host-local time. For extreme signed64 UTC outside the civil formatter's supported range, show a bounded unavailable/error message; epoch zero remains valid. POSIX seconds do not represent leap-second labels without a separate source convention.

12-hour digital time requires an explicit AM/PM indication: midnight 12 AM, noon 12 PM. 24-hour digital formatting uses 00 through 23. Analog dial geometry, second-hand policy and 24-hour-face behavior remain an explicit follow-up decision; do not claim conventional 12-hour dial plus a 24-hour label proves 24-hour analog parity. The first analog implementation can provide a textual equivalent and clearly document its chosen display policy while original behavior remains unverified.

## CB1 native view proposal and Qt gates

Use standard accessible labels/menus/buttons around an original QPainter analog face or a digital label; retain warm/slate surfaces, system font, clear hierarchy and subtle dividers consistent with the accepted UI. Avoid new custom fonts/art/dependencies. Text and controls remain legible at actual seven-inch logical scale, resized/enlarged-font layouts and Light/Dark/System. Proposed >=44 logical pixel controls, visible keyboard focus and named options provide touch and keyboard equivalents; this is an acceptance target, not compliance certification.

Expose a visible Options control, keyboard access and an explicit Back/Exit control in addition to the documented clock-background click. Hit routing distinguishes background/menu from countdown restart and alarm cancellation; clicking a timer must execute its specific action, not also open the menu. Escape closes a menu first and then returns from the view, without stopping any timer. Exact escape/default navigation is a replacement policy. Menu changes retain focus, selected values and provider state; failed commands show bounded plain-text errors and preserve shared state.

[Qt QWidget accessibility guidance](https://doc.qt.io/qt-6/accessible-qwidget.html) documents standard-widget interfaces and additional work for custom elements. A painted analog face must have an equivalent queryable textual time/zone/date and named actions; accessibility cannot depend on reading hand angles or color. State notifications should announce meaningful option/expiry changes rather than every second. Inspect actual platform accessibility roles/events and test VoiceOver/Orca where available; neither QAccessible metadata nor offscreen rendering establishes ADA/WCAG compliance.

Minimum Qt remains 6.4 Core/Gui/Widgets. Use existing QTimer/context-bound signals, QLabel/QPushButton/QMenu/QPainter and palette events; do not introduce QML/QtQuick or QtVirtualKeyboard. [QStyleHints current docs](https://doc.qt.io/qt-6/qstylehints.html#colorScheme-prop) mark colorScheme since 6.5 and setter since 6.8; use the existing 6.4-compatible palette approach and actual baseline build gate. [QDateTime](https://doc.qt.io/qt-6/qdatetime.html) documents validity/range and newer transition-resolution APIs; current docs are not blanket 6.4 evidence. Civil conversion must check supported baseline headers, validate results and test transitions independently. Big Clock rendering does not authorize choosing a DST scheduler policy.

## Two implementation paths, two steps ahead

| Path | First step | Second step | Recommendation / unresolved risk |
|---|---|---|---|
| A: standalone native Big Clock view | CB0 pure preferences + CB1 read-only injected clock/availability view, digital first with explicit unsupported analog state until original rendering is ready. | Root shared snapshot/timer integration, then analog face and truthful weather/alarm surfaces in separate audited increments. | Smallest bounded native increment; an incomplete preview must clearly disclose unsupported selections rather than imply parity. |
| B: reusable clock-content widget, shared with dashboard | CB0 + reusable original face/text/status component; dedicated window and dashboard both consume the same snapshot. | Expand full-window menu/options/timers while preserving compact/dashboard layout behavior and independent interaction regressions. | Reduces eventual renderer duplication but broadens initial layout/API coupling; root must freeze compact-versus-full composition and ownership first. |

Both paths require shared service injection and original art. Prefer A for the next verifiable slice, then extract a reusable renderer only if measured integration needs justify it. Neither path requires real weather or civil alarm code to proceed: unavailable provider states and supplied synthetic test snapshots allow truthful offline development. An approved provider/zone adapter is a separate prerequisite for those runtime features.
